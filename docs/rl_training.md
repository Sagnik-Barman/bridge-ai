# The RL card-play agent — what it is, how it's trained, and its honest limits

This doc is written for *you*, not just as code comments — you should be able
to explain every piece of this in an interview. It covers: what problem the
RL agent actually solves, the state/network/algorithm, how to run training
yourself, how to evaluate a checkpoint, and exactly what's simplified and
why. Nothing described here, and nothing in `rl/`, ever reads the uploaded
bridge book or any other copyrighted instructional material — every byte of
training data is generated by the program dealing itself random hands and
playing them out (self-play). See `docs/references.md` for the only sources
this project draws on.

## The problem being solved (and the one *not* being solved)

Bidding stays exactly the existing rules-based engine (`bidding/`) — that's
unchanged and deliberately not something RL touches, both because real
bridge bidding genuinely is an agreed rule system between partners (RL-ing
it doesn't make sense the way it does for, say, Go) and because bidding +
card play jointly is a much harder RL problem than either alone.

**Card play** is what the RL agent learns: given a hand, what's been played
so far, and the contract, which card to play. That's a well-defined
sequential decision problem with a clear reward signal (tricks won), which
is why it's the tractable, honest scope for a from-scratch RL project on a
placement-season timeline.

## Two very different settings, and why there are two of them

1. **Training** (`rl/env.py`): a *fully-known* self-play game. A random deal
   is dealt, a random declarer and strain are picked (bidding is skipped —
   see above), and the *same* network plays all four seats against itself,
   seeing the complete board at every decision. This is legitimate for
   training because within one self-play game, nothing is actually hidden —
   there's no "cheating," it's a full-information game by construction.
2. **Real gameplay** (`rl/rl_player.py`): actual bridge is imperfect
   information — a defender can't see declarer's and dummy's concealed
   cards. So at play time, the trained network is wrapped with the same PIMC
   (Perfect Information Monte Carlo) technique used for the DDS opponent
   (`cardplay/dds_player.py`): sample several plausible completions of the
   unseen hands, ask the network what it would do in each fully-known
   sample, and average its recommendations. This is the standard way to
   turn a full-information policy into a usable imperfect-information one
   without retraining — you're not reinventing anything here, this is how
   real bridge/poker/imperfect-info-game AIs commonly bridge that gap.

## State representation (`rl/features.py`)

Every decision is encoded from the *mover's own point of view* (this is
what makes one shared network able to play any of the four seats
meaningfully): a fixed-size vector of about 425 numbers —

- which cards the mover still holds (52 numbers, one-hot)
- which cards each of the other three seats (in relative seat order) still
  hold (3 × 52)
- up to three cards already played in the current trick, in play order (3
  × 52)
- the trump suit / no-trump (5, one-hot)
- tricks already won by the mover's side vs. the other side so far (2,
  normalized)
- how many cards have already been played into the current trick (1,
  normalized)

Illegal cards (not in hand, or not following suit when required) are
excluded via a separate 52-length legal-move mask, applied before the
network's raw output is turned into a probability distribution.

## Network (`rl/network.py`)

This is now a **PyTorch** network (`nn.Module`, Adam via `torch.optim`),
so it trains on your CUDA GPU when you run it on your own machine — see
"Setting this up on your machine" below. It started life as a from-scratch
NumPy implementation (forward pass, backprop, and an Adam step all
hand-written), because the cloud sandbox this project was originally built
in has no way to install PyTorch. That version is kept at
`rl/network_numpy.py` as a zero-dependency reference/fallback — genuinely
worth mentioning in an interview too, since walking through how you derive
the gradient for a masked softmax policy head by hand is arguably a
*better* story than "I called `nn.Linear`". Both versions implement the
exact same architecture and the exact same external interface (`forward`,
`policy`, `act`, `train_step`, `save`/`load`), so nothing else in `rl/`
cares which one is plugged in as `rl/network.py`.

Architecture: a small 2-hidden-layer MLP (425 → 128 → 64), ReLU
activations, with two heads on top of the shared trunk:

- **policy head** (64 → 52): logits over which card to play, turned into a
  probability distribution with a *masked* softmax (illegal cards get zero
  probability, not just low probability).
- **value head** (64 → 1): a scalar estimate of "how many of the remaining
  tricks will my side end up with from this position" — this is the
  baseline used to reduce variance in training (see below), the same role
  a value function plays in any actor-critic method.

This is a small network on purpose — a few hundred thousand parameters,
trainable on a CPU in minutes to hours, appropriately scoped for a
placement-season project rather than an attempt at a production-strength
system.

## Training algorithm: self-play REINFORCE with a value baseline

This is a basic actor-critic method, not a full AlphaZero-style MCTS
system (there's no search — just the policy network's direct output). Per
self-play game:

1. Play all 52 decisions of a full board (13 tricks × 4 seats), sampling
   each seat's card from the network's current policy (stochastic, for
   exploration).
2. At the end, each decision is credited with a **return-to-go**: how many
   of the tricks from *that decision's own trick onward* its side ends up
   winning (see "A second real result" below for why this isn't simply
   "the final trick count" repeated at every decision, which is what an
   earlier version of this project did). The value head's baseline
   (`return − predicted_value`, i.e. the *advantage*) is what keeps the
   resulting gradient updates usable on top of that.
3. Policy gradient update: for the action actually taken, push the
   network's output probability up if the advantage was positive (this
   decision was made in a game that, in hindsight, went better than the
   value head expected for that side) and down if negative. This is the
   textbook REINFORCE-with-baseline update, restricted to the legal-move
   mask.
4. Value head update: ordinary squared-error regression towards the
   observed return.

Both updates happen together in one gradient step per training batch
(`rl/train.py`'s `train_step`), and parameters are updated with Adam.

## Setting this up on your machine (CUDA + VS Code)

This was built and tested in a cloud sandbox with no GPU and no way to
install PyTorch at all, so none of the steps below have been run by me —
follow them, and if anything doesn't match what you see, that's real
signal to debug, not a sign you did something wrong.

1. **Confirm you actually have an NVIDIA GPU and driver.** Open a terminal
   (VS Code's integrated terminal is fine — `` Ctrl+` ``) and run:
   ```
   nvidia-smi
   ```
   If that fails, you don't have a working NVIDIA driver installed, and
   training will fall back to CPU (still works, just slower — everything
   in `rl/` auto-detects this, nothing crashes either way).
2. **Create and select a virtual environment in VS Code**, from the
   project root (`D:\Projects\bridge-ai`):
   ```
   python -m venv .venv
   .venv\Scripts\activate
   ```
   Then `Ctrl+Shift+P` → "Python: Select Interpreter" → pick the one
   inside `.venv`, so VS Code's terminal, debugger, and "Run" button all
   use the same environment you install packages into.
3. **Install PyTorch with CUDA support.** The exact pip command depends on
   your CUDA version, so use the official selector at
   [pytorch.org/get-started/locally](https://pytorch.org/get-started/locally/)
   (choose Stable, your OS, Pip, Python, and the CUDA version matching what
   `nvidia-smi` reported) rather than trusting a hardcoded command here —
   it'll look something like:
   ```
   pip install torch --index-url https://download.pytorch.org/whl/cu121
   ```
4. **Install everything else:**
   ```
   pip install -r requirements.txt
   ```
   (`endplay` is optional — see the main README — everything else here
   works without it.)
5. **Verify PyTorch can actually see your GPU:**
   ```
   python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0) if torch.cuda.is_available() else None)"
   ```
   `rl/train.py` prints this same check at the start of every run, so
   you'll see immediately if it's training on `cpu` when you expected
   `cuda` (usually means step 3 installed a CPU-only wheel — re-check the
   selector's exact command).
6. **Run the tests** (from the project root, venv active) to confirm the
   whole `rl/` pipeline works in your environment before spending real
   training time:
   ```
   python run_tests.py
   ```
7. **Train.** See the commands below — nothing here needs a `--device`
   flag unless you want to force CPU or CUDA explicitly (`--device cpu` /
   `--device cuda`); the default auto-detects.

## Running it yourself

```bash
# Train from scratch. Each iteration plays `--games-per-iter` self-play
# games and does one gradient update on the resulting batch of decisions.
python -m rl.train --iterations 500 --games-per-iter 20 --out rl/checkpoints/latest.pt

# Resume/continue training an existing checkpoint:
python -m rl.train --iterations 500 --resume-from rl/checkpoints/latest.pt --out rl/checkpoints/latest.pt

# Evaluate a checkpoint against the existing heuristic bot (and, if
# `endplay` is installed, against double-dummy-optimal par) on fresh deals:
python -m rl.evaluate --checkpoint rl/checkpoints/latest.pt --num-deals 100

# Train with opponent diversity (see "A real result" below for why):
python -m rl.train --iterations 5000 --games-per-iter 20 --heuristic-opponent-prob 0.5 --out rl/checkpoints/latest.pt
```

## A real result: pure self-play underperformed the heuristic bot

Worth documenting honestly, because it's a genuinely useful finding, not
just a bug: a checkpoint trained for 5000 iterations of *pure* self-play
was evaluated on 300 fresh random deals and came out slightly *worse*
than the plain heuristic bot as declarer:

```
RL agent as declarer:          5.91 tricks/board avg
Heuristic bot as declarer:     6.34 tricks/board avg
Double-dummy optimal (par):    8.43 tricks/board avg
```

That gap (confirmed on 300 deals, not just an early noisy 30-deal check)
is real, and the likely cause is a known failure mode of pure self-play:
the network only ever played against copies of itself, so it could
converge to a policy well-adapted to its own quirks without ever being
forced to handle a genuinely different playing style. Self-play
improving relative to earlier versions of itself does not guarantee it
generalizes to an opponent from outside that self-play loop — and the
heuristic bot, with its fixed hand-written rules, is about as
out-of-distribution an opponent as it gets relative to a network that has
only ever seen itself.

`rl/env.py`'s `play_game(..., heuristic_side=...)` and `rl/train.py`'s
`--heuristic-opponent-prob` fix this directly: a training run can now mix
in games where one randomly chosen side (NS or EW) is played by the
heuristic bot instead of self-play, so the network is forced to learn to
handle that specific opponent, not just its own mirror image. Only the
network's own decisions are ever used for the policy gradient update —
the heuristic bot's moves are just part of the environment it's reacting
to, so no importance sampling correction is needed. Re-train with
`--heuristic-opponent-prob 0.5` (or similar) and re-run `rl.evaluate`
to see whether this closes the gap.

## A second real result: opponent diversity alone didn't fix it either

It didn't. A checkpoint retrained for 5000 iterations with
`--heuristic-opponent-prob 0.5` scored almost identically on the same
300-deal evaluation:

```
RL agent as declarer:          5.90 tricks/board avg
Heuristic bot as declarer:     6.29 tricks/board avg
```

Reporting this straight rather than quietly trying again until something
looked better: this ruled out the self-play-generalization theory as the
*dominant* cause. The real tell was in the training log itself, not the
final number — `rl/train.py`'s periodic evaluation (every 20 iterations)
showed RL-as-declarer bouncing between roughly 5.1 and 6.6 tricks for the
*entire* 5000-iteration run, with no upward trend at any point, and the
value head's loss never settled into a clear downward trend either. That
pattern — flat from early training onward, not "started fine, then failed
to transfer" — points to something more fundamental than opponent
mismatch: the reward itself.

The original reward was a purely terminal one: every one of a hand's ~13
decisions was credited with the exact same number (the side's final
trick count for the whole game). That's the mathematically correct
return-to-go for a reward that only ever fires at the very end — but it's
also a genuinely hard credit-assignment problem for REINFORCE, a
high-variance algorithm to begin with: a decision made in trick 2 and a
decision made in trick 12 get *identical* training signal, even though
one of them can still affect 11 more tricks of play and the other can't.
High variance in the gradient estimate is precisely what causes training
to plateau instead of improving — exactly what the flat log showed.

The fix (now implemented, `rl/env.py`'s `decisions_to_training_batch`):
decompose the final trick count into its natural per-trick components. A
side's total tricks won is exactly the sum, over all 13 tricks, of "did
this side win this specific trick" (0 or 1) — the same total, just
attributed to the tricks that actually earned it instead of smeared
uniformly across every decision in the hand. A decision's return-to-go is
now the sum of those per-trick indicators from its own trick onward: for
a first-trick decision this is identical to the old formulation (the
whole game's total, exactly as before), but for a late-hand decision it's
a much smaller, much more specific number — shrinking the variance of the
training signal for exactly the decisions that most need it. This is a
real algorithmic change (a form of reward shaping via reward
decomposition), not a hyperparameter tweak, and it changes what
`rl/train.py`'s and `rl/evaluate.py`'s printed "tricks" numbers are being
optimized against under the hood, though not what they mean when read.

Re-train from scratch (an existing checkpoint was fit against the old
reward scale, so `--resume-from` isn't appropriate here) and re-evaluate
on 300 deals to see whether this actually breaks the plateau. Report
whichever result comes back honestly, including a null result — a
correctly diagnosed and directly addressed pair of RL training pathologies
(self-play generalization, and reward sparsity/credit assignment) is a
substantive finding for a resume project on its own, independent of
whether trick counts have overtaken the heuristic bot yet.

## A third real result: reward shaping didn't move the needle either — and why we stopped here

Re-training from scratch with per-trick return-to-go (still with
`--heuristic-opponent-prob 0.5`) gave: **RL agent as declarer: 5.85
tricks/board avg, heuristic bot as declarer: 6.29 tricks/board avg** (300
held-out deals). That's the third training configuration in a row landing
in essentially the same place:

| Configuration | RL as declarer | Heuristic as declarer |
|---|---|---|
| Pure self-play | 5.91 | 6.34 |
| + opponent diversity | 5.90 | 6.29 |
| + per-trick reward shaping | 5.85 | 6.29 |

Two genuinely different, well-motivated algorithmic fixes (mixing in a
heuristic opponent to close the self-play generalization gap; decomposing
a sparse terminal reward into per-trick return-to-go to fix credit
assignment) each produced *zero* measurable change. That pattern — not
"it got a bit better each time" but "it didn't move at all" — is itself
suspicious enough to be worth checking for a more basic problem before
concluding "this is just where a small from-scratch MLP tops out": a bug
in the training mechanics themselves (the optimizer, the policy-gradient
math, the masked softmax, the actor-critic baseline) would produce
exactly this signature, since no amount of fixing the *bridge-specific*
half of the problem (opponent style, reward shape) would help if the
*generic* half (does gradient descent on this loss actually improve the
policy at all) were broken.

**The sanity check.** Before accepting the plateau as a real ceiling, the
training loop itself (`PolicyValueNet.train_step` in `rl/network_numpy.py`
— the same REINFORCE-with-baseline math as the PyTorch version in
`rl/network.py`, which mirrors it deliberately) was tested in isolation, on
a synthetic task that has nothing to do with bridge: a handful of fixed
random "contexts" (feature vectors of the same size the real network
uses), each with a small legal-action mask and one designated "correct"
action, rewarded 1.0 for picking it and 0.0 otherwise — the same shape of
problem (masked softmax over many actions, sparse binary reward,
actor-critic baseline) with none of bridge's sequential/partial-information
complexity. If the training mechanics are sound, average reward should
climb from random-guessing toward 1.0.

It did — cleanly and fast: starting near the random-guessing baseline
(~0.17 with 6 legal actions per context), average reward crossed 0.85 by
iteration 80 and settled at ~0.999-1.000 by iteration 200 (of 400), with
the final greedy policy solving all 8 synthetic contexts exactly. **This
confirms the optimizer, the policy-gradient derivation, the masked
softmax, and the value-head baseline are all implemented correctly** —
there is no bug in the generic training loop. Whatever is capping the
bridge results at ~5.85-5.91 tricks/board is specific to the bridge
problem itself, not a broken pipeline underneath it.

**The honest conclusion.** Given a correctly-implemented training loop,
two real algorithmic fixes for the two most likely bridge-specific
pathologies, and still no measurable improvement, the most likely
remaining explanations are the ones that require materially more
engineering to test, not another quick fix: the ~360-dimensional one-hot
state encoding may not give the network enough signal to distinguish
"good" from "bad" plays as cleanly as the toy task's contexts did; 100,000
self-play games (5000 iterations x 20 games) may simply be too few
samples for a from-scratch policy to find good play in a combinatorially
large 52-card action space with no search; and REINFORCE without any form
of planning/lookahead is a genuinely weak algorithm for a game this deep
compared to, say, imitation learning from a stronger source or adding
search on top. Chasing any of those properly (a supervised imitation warm
start, a much longer training run, or restructuring the features) is real
additional engineering, not a tweak — and was deliberately decided *not*
to be the next step here, in favor of writing this up honestly as the
project's actual, defensible finding.

**For the resume/interview version of this story**: "I built a from-scratch
self-play RL pipeline (state encoding, hand-rolled + PyTorch policy/value
networks, an actor-critic training loop verified correct via an isolated
synthetic sanity check), diagnosed two real training pathologies
(self-play generalization gap, sparse-reward credit assignment), fixed
both correctly, and when the fixes didn't move the needle, used a targeted
diagnostic to rule out a pipeline bug rather than guessing — concluding
the remaining gap is a genuine capacity/algorithm limit of small-MLP
REINFORCE without search, not an implementation error." That is a complete
and honest engineering narrative, and arguably a *better* one for a
Quant/AI-ML interview than a checkpoint that happened to beat a simple
heuristic bot would have been on its own — it demonstrates the diagnostic
process, not just an outcome.

**A note on CUDA specifically:** this network is small (a few hundred
thousand parameters) and each training step's batch is one self-play
game's worth of decisions (tens to low hundreds of examples), so the
GPU-vs-CPU speedup here isn't the dramatic kind you'd see training a large
model — a lot of the wall-clock cost is generating self-play data (Python
game logic, not matrix math) rather than the gradient step itself. CUDA
still helps, and it's worth having set up correctly, but if you watch
`nvidia-smi` during a run and see low GPU utilization, that's expected,
not a bug: increase `--games-per-iter` to batch more decisions per
gradient step if you want the GPU doing proportionally more of the work.

**How long does this take, and how good will it get?** Each self-play
game is a few hundred forward passes through a small MLP — fast (the
smoke run during development, on CPU, did ~4 games + one gradient step
in well under a second). The real cost is *how many* iterations it takes
to learn something non-trivial: expect low hundreds to low thousands of
iterations (tens of thousands of self-play games) before it's reliably
beating the heuristic bot as declarer, and getting genuinely close to
double-dummy-optimal play is a much larger undertaking than this project's
timeline allows — full-strength bridge AI (GIB, Jack, WBridge5-class
programs) represents years of specialized engineering, most of it in
highly-optimized search, not just a bigger network. **Be honest about this
in an interview**: the value of this component is the correctly-built RL
pipeline (state representation, self-play data generation, a working
actor-critic implementation from scratch, and an honest evaluation
methodology against a real baseline), not a claim of superhuman play.

`rl/train.py` runs a `rl/evaluate.py` check every `--eval-every` iterations
and prints RL-vs-heuristic average tricks on held-out deals, so you can
watch the trend line yourself and decide when it's trained "enough" for
what you need (a resume demo vs. genuinely strong club-level play are very
different bars).

## A fourth attempt: imitation warm start

After three training configurations (pure self-play, +opponent diversity,
+per-trick reward shaping) all landed at essentially the same result, and
a synthetic sanity check ruled out a bug in the training loop itself (see
"A third real result" above), the honest remaining explanations were: the
state encoding may not carry enough signal, and/or REINFORCE from random
weights in a 52-card action space with no search is simply slow to find
anything good in ~100,000 self-play games. The first of those is hard to
fix without a redesign; the second has a standard, well-known answer:
**don't start from random weights.**

**The idea.** Before self-play begins, pretrain the policy network with
ordinary supervised learning (behavior cloning) on a pile of (position,
correct card) examples, so self-play only has to *refine* an
already-reasonable policy instead of discovering bridge from nothing. This
is the same idea behind AlphaGo's original supervised pretraining phase,
scaled down to fit this project.

**The honest catch: this codebase doesn't have a validated way to get the
true double-dummy-optimal card at an arbitrary mid-hand position.** Two
real primitives exist, and each covers only part of the problem:

- `cardplay/endgame_solver.py`'s alpha-beta search is genuinely exact —
  but only tractable up to a handful of cards left per hand (see
  `docs/endgame_solver.md`).
- `cardplay/dds_player.py`'s DDS/PIMC-informed play is only meaningfully
  different from the heuristic bot at a fresh trick *lead* — by its own
  module docstring, it falls back to the same heuristic rules mid-trick,
  because this project's DDS binding doesn't expose (or, more precisely,
  hasn't been able to *validate* — same caution as `pbn_loader.py`) a
  "best card mid-trick" primitive.

So `rl/generate_labels.py` labels exactly two situations — near the end of
a hand (exact, via the endgame solver, at a higher card limit than the
live Analyzer feature since offline generation can afford to wait longer
per position) and trick leads earlier in the hand (DDS/PIMC-informed, when
`endplay` is installed) — and leaves every other decision (mid-trick,
many cards still out) unlabeled rather than mislabeling it with the
heuristic bot's own choice, which would teach the network nothing new.
That's a real, useful, but *partial* teacher, not a full double-dummy
oracle — say so plainly if this comes up in an interview.

**Running it -- time a small batch first.** `rl/generate_labels.py`'s
cost is dominated by `endgame_solver` calls, and this project's own
measurements (`docs/endgame_solver.md`) already showed that cost grows
several-fold per additional card, not gradually -- an early version of
this script defaulted `--endgame-limit` to 8 reasoning "offline can
afford to wait longer per position," and that was wrong: with roughly
half of every hand's decisions falling at 8-or-fewer cards left, and many
of those individual searches burning through the full 200,000-node
budget before giving up, a few thousand deals at limit 8 measured out at
multiple *hours*, not minutes. The default is now 6 (matching the rest of
this codebase), but "how long will N deals actually take" still depends
on your machine, so run a small batch first and read the progress line's
ETA before committing to a big one:

```bash
python -m rl.generate_labels --num-deals 100 --out /tmp/probe.npz
#   ...50/100 deals, 812 labels so far (23s elapsed, ~23s remaining)
# scale --num-deals from that rate to whatever total time you're willing
# to spend, then run the real thing:
python -m rl.generate_labels --num-deals 3000 --out rl/checkpoints/imitation_labels.npz
python -m rl.pretrain --labels rl/checkpoints/imitation_labels.npz --out rl/checkpoints/warm_start.pt
python -m rl.train --resume-from rl/checkpoints/warm_start.pt --iterations 5000 \
    --games-per-iter 20 --heuristic-opponent-prob 0.5 --out rl/checkpoints/latest.pt
```

The last command is your existing self-play training command, unchanged
except for `--resume-from` pointing at the warm-started checkpoint instead
of starting from random weights — `rl/train.py` already supported
resuming, so nothing there needed to change. `rl/generate_labels.py` is
dependency-free (pure Python + NumPy; DDS-informed lead labels are simply
skipped if `endplay` isn't installed, with a printed note saying so), so
you can build the dataset even before setting up CUDA. `rl/pretrain.py`
adds a `pretrain_step` method to both `PolicyValueNet` implementations
(plain cross-entropy on the masked policy head; the value head is left
alone here, since these labels don't come with a return estimate to train
it toward — self-play trains that soon enough regardless).

Both `pretrain_step` implementations, and `rl/generate_labels.py`'s
position-selection logic, are covered by dependency-free tests
(`tests/test_rl_network_numpy.py`, `tests/test_generate_labels.py`) that
run without torch or endplay — a small synthetic-labels convergence check
mirroring `scripts/rl_sanity_check.py`'s method confirmed the supervised
step actually learns before this was ever run against real bridge
positions.

**What to expect, honestly**: this should help with the "random
initialization in a huge action space" half of the plausible explanations
above. It does nothing for the "state encoding might not carry enough
signal" half, and it's still a partial teacher (leads and endgames, not
the middle of the hand) — so treat a re-evaluation after this as another
honest data point, not a guaranteed fix. Report whatever comes back,
including a null result, the same way the first three attempts were
reported here.

**The actual result, run end-to-end**: a fourth null result. 1000 deals of
imitation labels (23,883 labeled decisions, endgame-solver only — `endplay`
wasn't installed for this run, so no DDS-informed lead labels), 10 epochs
of pretraining, then 5000 self-play iterations resumed from the
warm-started checkpoint, evaluated on the standard 300-deal benchmark:

```
RL agent as declarer:          5.86 tricks/board avg
Heuristic bot as declarer:     6.40 tricks/board avg
```

Virtually identical to the third attempt's 5.85 vs 6.29 — the in-training
30-deal eval briefly showed a better-looking 6.00 vs 6.50 at iteration
5000, but that was flagged as likely noise from a small sample *before*
running the full evaluation, and the full 300-deal number confirmed it was
exactly that. Four structurally different interventions (pure self-play,
opponent diversity, per-trick reward shaping, imitation warm start) now
land in the same 5.85-5.91 vs 6.29-6.40 band. That's a strong pattern
pointing at a structural ceiling — the state encoding and/or the
"no-lookahead policy network" algorithm class itself — rather than
anything fixable by another training-loop tweak. See "A fifth attempt"
below for the one remaining lever that changes something other than the
training loop.

## A fifth attempt: search on top of the policy

Four attempts at training a *better* policy all landed in the same band.
The one remaining honest lever that doesn't just re-run the same idea a
fifth way is to stop asking the network to do everything itself: give it
actual lookahead at decision time, the way real double-dummy-solver-backed
players (and this project's own `dds_player.py` / `game/session.py`
Analyzer) already do — fall back to exact search near the end of the hand,
where it's cheap enough to be tractable, and use the learned policy only
where an exact search isn't affordable.

**The idea.** `cardplay/endgame_solver.py`'s alpha-beta search is already
proven exact (it's what generated the imitation-learning labels above) and
already known to reliably finish within a second or two at up to 6 cards
left per hand. `rl/evaluate.py` now has `_rl_policy_with_endgame_search(net,
endgame_limit)`: a hybrid decision function that calls `solve_endgame`
whenever the mover has `<= endgame_limit` cards left, and only asks the
network when the position is too large for that. This changes nothing
about what the network learned — same checkpoint, same weights — it only
changes how much of the game is decided by exact search versus by the
network's own (still-modest) judgment.

**The honest catch.** This is measured in `rl/evaluate.py` specifically
because evaluation is full-information (the network already sees every
hand there, matching how it was trained) — `solve_endgame` needs full
information to search at all. Real gameplay in the app is NOT
full-information (a defender can't see declarer's and dummy's hidden
cards), so this hybrid is *not* wired into `rl/rl_player.py` (the real
opponent used by "Play against RL") as of this writing — doing that
would need the same PIMC sampling `rl_player.py` already does for the
network, applied to the endgame solver too, which is a real follow-up but
separate work, not done here. Treat this as measuring an upper bound on
what search-assisted play could do for this network, not a shipped
gameplay feature yet.

**Running it:**

```bash
python -m rl.evaluate --checkpoint rl/checkpoints/latest.pt --num-deals 300 --seed 1 \
    --endgame-search-limit 6
```

This plays every deal four ways (plain RL as declarer, heuristic as
declarer, RL+endgame-search as declarer, and heuristic+endgame-search as
declarer — the credit-attribution control described below — all against
the same heuristic defense) and prints all four averages, so the hybrid's
effect is a direct, measured number against the same baseline already
reported above — not an assumption. It roughly quadruples the runtime of a
plain `rl.evaluate` call (four playouts per deal instead of two, and the
endgame searches themselves aren't free), so expect it to take longer than
the 300-deal runs you've done before; time a smaller `--num-deals` first
if you want an ETA.

Covered by `tests/test_rl_evaluate.py` (torch-gated, like
`tests/test_rl_network.py`): confirms both hybrids return exactly the
exact-solver's answer within the search limit, fall back to their
respective plain policy above it, and that turning them on doesn't change
the existing plain-RL/heuristic numbers in `evaluate_vs_heuristic`.

**The credit-attribution control.** The first run of this (300 deals,
seed 1) came back genuinely positive:

```
RL agent as declarer:                                5.85 tricks/board avg
Heuristic bot as declarer:                            6.37 tricks/board avg
RL + endgame search (<=6 cards) as declarer:          6.59 tricks/board avg
```

RL+search finally beat the plain heuristic bot — the first time in this
entire project that any RL-based configuration has. Before reporting that
as "search fixes it," the honest next question is whether the *network*
is contributing anything, or whether the exact search alone is strong
enough to win regardless of what policy sits above it. `rl/evaluate.py`'s
`_heuristic_policy_with_endgame_search` answers this directly: it's the
identical search, bolted onto the plain heuristic bot instead of the
network, as a control. A second run (same seed, same checkpoint) added
this control and got:

```
RL agent as declarer:                                     5.84 tricks/board avg
Heuristic bot as declarer:                                6.28 tricks/board avg
RL + endgame search (<=6 cards) as declarer:              6.63 tricks/board avg
Heuristic + endgame search (<=6 cards) as declarer:       7.14 tricks/board avg
```

(The small run-to-run drift in the RL and heuristic baselines — 5.85→5.84,
6.37→6.28 — is consistent with floating-point non-determinism in the
network's GPU inference occasionally flipping a near-tied `argmax`, not a
bug; it doesn't change the conclusion below.)

**The honest read: the search is doing essentially all of the work, and
the trained network is still worse than the heuristic even with search
added to both.** The heuristic's gain from search (6.28 → 7.14, +0.86) is
at least as large as the RL policy's gain from search (5.84 → 6.63,
+0.79) — if the network were adding real value on top of the search, its
gain should have been *larger* than the heuristic's, not roughly the same
or smaller. And directly: heuristic+search (7.14) beats RL+search (6.63)
by half a trick. So "search on top" is a real, working technique — it's
just that it works better on top of the simple hand-written heuristic
than on top of five training runs' worth of learned policy. That's a
fifth consistent data point that the trained network's mid-hand judgment
is weaker than the heuristic bot's own rules, not a fifth data point that
gets erased by finally finding a lever that helps.

**What to actually say about this in an interview**: exact search near
the end of a hand is a real, measurable win (+0.79 to +0.86 tricks/board,
reproduced on two runs) — that's a legitimate, load-bearing result from
this project's own from-scratch alpha-beta solver. The trained RL policy,
across five structurally different attempts (pure self-play, opponent
diversity, reward shaping, imitation warm start, and now search-augmented
inference), has never beaten the project's own hand-written heuristic bot
in an apples-to-apples comparison. The honest diagnosis is that the
combination of this state encoding, this network size, and REINFORCE
without search is not enough training signal to out-learn a dozen
hand-written bridge rules in the time available — not a training-loop bug
(ruled out by the synthetic sanity check), and not fixable by "train
longer" alone (four attempts already tried variations of that). Reporting
this precisely — what worked (search), what didn't (five attempts at a
better learned policy), and why the two don't get to share credit — is a
stronger interview answer than either an inflated "RL beats heuristic"
claim or an incomplete "we added search and it worked" claim that skips
the control that shows search would have worked on anything.

## Wiring into the app

Once you have a checkpoint at `rl/checkpoints/latest.pt` (the default
path `game/session.py` looks for), start a new game and choose "Play
against RL" from the opponent picker. If no checkpoint exists yet, that
mode transparently falls back to the standard heuristic bot (the app tells
you this via the opponent status text) — it never silently pretends to be
smarter than it is.

## What's honestly out of scope

- No bidding RL — bidding is, and stays, the rules-based engine.
- The self-play training environment uses full information; only the
  PIMC-wrapped inference path (`rl/rl_player.py`) handles the real
  imperfect-information setting, and that wrapper is an approximation
  (averaging a handful of samples), not exact. The endgame-search hybrid
  (see "A fifth attempt") is measured only in the full-information
  `rl/evaluate.py` harness for this same reason — it is not wired into
  real (imperfect-information) gameplay as of this writing.
- No claim is made about how many training iterations "are enough" — that
  depends entirely on how much compute time you give it before your
  deadline; run `rl/evaluate.py` periodically and judge for yourself.
- **As trained, the network never beats the heuristic bot on its own
  judgment.** Five structurally different attempts — pure self-play,
  +opponent diversity, +per-trick reward shaping, an imitation warm start,
  and search-augmented inference — all confirm the same thing: this
  state encoding, network size, and REINFORCE-without-search setup does
  not out-learn the project's own hand-written heuristic rules in the
  time available (see "A third real result", "A fourth attempt", and "A
  fifth attempt" above). A synthetic sanity check ruled out a training-loop
  bug. This is reported as the project's honest result, not hidden or
  glossed over — the "Play against RL" opponent in the app is real and
  works, it's just not yet stronger than the rule-based bot it's compared
  against.
- **Exact endgame search near the end of a hand is a real, separately
  demonstrated win** (+0.79 to +0.86 tricks/board, reproduced on two
  300-deal runs — see "A fifth attempt"), but a credit-attribution control
  (the same search bolted onto the plain heuristic instead of the network)
  showed the heuristic gains at least as much from it as the RL policy
  does, and heuristic+search still beats RL+search outright. So this
  project's honest conclusion is two separate findings, not one: search
  helps (genuinely, measurably), and the trained policy specifically does
  not add value beyond the heuristic, with or without search. Don't
  conflate "RL+search beat the plain heuristic" with "the RL component
  works" — the control rules that reading out. No further hyperparameter
  sweep or training-loop variant was attempted beyond what's documented
  above — a concrete, named stopping point, not a silent gap.
